# 分支模型与 CI 触发规则

## 一、设计原则

1. **每个车型一条专属开发分支。** 车型之间不共享开发分支。
2. **日常开发不跑完整 CI。** 只有推送到车型正式分支时才跑完整流水线。
3. **`main` 是门面。** 只放文档、硬件定义与发布产物，不放日常业务代码。

## 二、分支职责

| 分支 | 角色 | 生命周期 | 触发 CI |
|---|---|---|---|
| `mecanum/develop` | 麦轮日常开发 | 长期 | 否 |
| `differential/develop` | 差分日常开发 | 长期 | 否 |
| `feat/mecanum` | 麦轮正式分支 | 长期 | 是，完整 |
| `feat/differential` | 差分正式分支 | 长期 | 是，完整 |
| `main` | 项目门面与发布 | 永久 | 是，只跑文档检查 |

## 三、工作流

```
<车型>/develop  ──推送──▶  feat/<车型>  ──合并──▶  main
   （日常提交）              （完整 CI）              （完整 CI + 发布）
```

### 第一步：日常开发

在 `<车型>/develop` 上自由提交。不触发完整 CI。可选的轻量检查见第四节。

### 第二步：推送到正式分支

`<车型>/develop` 的内容合入 `feat/<车型>`。这一步触发完整流水线。CI 不通过就不能进入下一步。

### 第三步：合入 main

`feat/<车型>` 通过 CI 后合入 `main`。

`main` 只放项目门面文档，不放业务代码。因此 `main` 的 CI **只跑文档检查**，不编译、不跑测试。

## 四、轻量检查

日常分支可选开启轻量检查，只做与内容相关的快速校验：

- 引脚表与 `.ioc` 的一致性
- 文档链接有效性

轻量检查不跑编译与测试，避免拖慢日常提交。

## 五、并发控制

| 分支 | 并发策略 |
|---|---|
| `feat/<车型>` | `cancel-in-progress: true`，只保留最新一次 |
| `main` | 同一分支只保留最新一次 |

原因：`main` 只做文档检查，很快，取消旧运行没有风险。

## 六、文档改动跳过

只改文档的提交用 `paths` 过滤，不触发编译与测试。

**注意**：被跳过的检查如果被设为必需检查，PR 会一直等待而无法合并。解决办法是给必需检查配套一个总是执行、结果总是成功的同名 job，由它判断是否需要跑真正的测试。

## 七、必需检查清单

设为必需检查的项目：

| 检查名 | 内容 |
|---|---|
| `firmware-build` | 固件全量编译 |
| `host-tests` | 主机侧单元测试与集成测试 |
| `static-analysis` | 静态分析与告警零容忍 |

## 八、分支保护建议

对 `feat/<车型>` 开启：

- 禁止直接推送，必须走 PR。
- 必需检查全部通过才可合并。
- 合并前分支必须与目标分支同步。
